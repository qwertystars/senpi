## 2026-11-11 - Pool refusals state their unblock instant (senpi#2)

### What changed

- `packages/ai/src/utils/retry-hint.ts`: new `parseStatedRetryInstantMs(message, nowMs?)` reads the
  anthropic-subscription pool refusal's `Soonest automatic retry: <ISO-8601>` instant and returns the
  remaining milliseconds. Only that phrase matches; an unrelated ISO timestamp in the text is ignored.

### Why

- The pool names the exact instant it can serve again, but the in-turn scheduler could not read it, so
  a refused session burst 2s/4s/8s/16s/32s retries before that instant. Measured on 12 session logs:
  66 refusals in 4 runs, all zero-token; reading the instant removes 62 of them.

### Why an extension could not handle it

- The value is parsed by the retry scheduler inside `AgentSession`, which runs before any model turn is
  made; an extension receives no event for a locally refused request and cannot alter the next retry.

### Expected merge conflict zones

- LOW: the marker helpers block in `retry-hint.ts`; `parseStatedRetryInstantMs` is additive and no
  existing parser changed behaviour.

## 2026-11-11 - Defer to a pool refusal's stated unblock instant (senpi#2)

### What changed

- `packages/coding-agent/src/core/agent-session.ts`: `_getProviderRetryDelayMs` falls back to
  `parseStatedRetryInstantMs` after the marker and 429-hint parsers; the tiered 429 branch ends the
  in-turn attempt when the stated instant is further away than `provider.maxRetryDelayMs`, so the
  goal's provider-retry wake (`providerRetryAt`) resumes at the stated time instead of burning the
  retry budget before it.

### Why

- `"rate limit or auth errors"` matches the 429-class regex, so the legacy `maxRetryDelayMs` gate was
  skipped; tier2 clamped a 430s-11,776s wait to 300s per attempt and spent the same 6-attempt ladder.
  Measured: 66 zero-token refusal turns in 4 lead-03 runs become 4 (one probe per run).

### Why an extension could not handle it

- The decision lives in the retry event path that runs after `agent_end`; no model turn exists on a
  locally refused request, so an extension cannot inject guidance or suppress the in-turn retry.

### Expected merge conflict zones

- MEDIUM: `_handleRetryableError`'s 429-class branch and `_getProviderRetryDelayMs` in
  `agent-session.ts`; both edits are short and sit beside existing tier logic.

## 2026-11-11 - Configurable 40 KiB model-facing output budget (senpi#2)

### What changed

- `packages/coding-agent/src/core/tools/truncate.ts`: `DEFAULT_MAX_BYTES` 50KB -> 40KB (~10k tokens at
  chars/4), `SENPI_TOOL_OUTPUT_MAX_BYTES` override through `resolveOutputMaxBytes()`, and
  `formatTruncationNotice()` for an explicit head footer
  (`[truncated - refetch with offset=N ...]`) and tail footer (`[truncated - ... Full output: path]`).
- `read.ts` uses the head notice (the user `limit` path keeps its shorter wording); `bash.ts` and
  `output-accumulator.ts` use the tail notice and the resolved budget. Small outputs are unchanged.
- `packages/agent/src/harness/utils/truncate.ts` takes the same 40 KiB default so the harness reader
  and the coding-agent reader stay byte-compatible; the harness bash assertion now expects 40.0KB.
- `packages/agent/src/harness/utils/segmented-read-view.ts`: the structural fold gate now uses its
  own input window (2,000 lines, 50 KiB) instead of "the raw read was truncated", so a 40-50 KiB
  `.js`/`.json` file still folds into a compact view with reread offsets rather than being
  byte-truncated into a raw head.

### Why

- Tool text above the 10k-token line carried 37,128 tokens in the measured corpus; the ceiling is now
  one configurable constant shared by read, bash, grep's byte stop and codemode's spill threshold.

### Why an extension could not handle it

- Truncation happens inside each tool's result assembly, below the extension API; an extension cannot
  rewrite a built-in tool's returned content before it enters context.

### Expected merge conflict zones

- HIGH: upstream rewrites `truncate.ts`/`read.ts` notices periodically. The edits are the constant, two
  helpers and three notice call sites; test assertions in `test/tools.test.ts` pin the new footer.
